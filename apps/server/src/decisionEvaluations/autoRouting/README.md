# Auto mode routing pilot (T3-359)

Advisory experiment: can the bounded decision engines (Jev, Luna) recommend, from a request's text alone, four separate things that an Auto mode would need: the project, the workflow (chat, solo, shape, lead), the difficulty of the main model, and the tier of a delegated worker? It consumes the shared `DecisionService` from T3-350 and changes no role, default, model list, UI or dispatch. Everything here is a shadow recommendation scored after the fact.

## Outcome: revise, do not enable anything

- **Subagent tier is the one decision where the engines helped, and it is not yet proof.** On the 20 held-out cases whose two blind labelers agreed, Jev chose the labelled tier in 18, Luna in 19, the current behaviour (always the demanding worker) in 15, the frozen keyword rule in 13 and always-routine in 5. Both engines never sent demanding work to the routine tier (0 under-provisioned cases; the keyword rule did so 6 times). Wilson 95% intervals overlap (Jev 0.70-0.97, Luna 0.76-0.99, current 0.53-0.89); no significance claim is made.
- **The saving is small and assumed.** With a routine worker costing 1 unit, a demanding worker 4 and a wrongly routine-routed demanding task paying again at the demanding price plus half a unit of correction, the 20 scored cases cost 71 (Jev), 68 (Luna), 80 (current), 77 (keyword) and 87.5 (always-routine); at 10 units 173, 164, 200, 173 and 177.5; at 2 units 37, 36, 40, 45 and 57.5. That is 11-15% below the current behaviour at 4 units. The engines picked the routine tier for only 4 (Jev) and 6 (Luna) of 32 cases, so the saving is a handful of cases. The cost ratio is an assumption, not a measurement: no real worker cost was observed.
- **Quality did not move in the downstream check, but the check could not separate the tiers.** Six read-only investigation tasks about this repository (three plain, three that look simple but have a second location a shallow search misses) went to the routine worker (`chore-worker`, deepseek-v4.1-flash, low) and the demanding worker (`implementation-worker`, gpt-6.1-sol, medium), once each, with behaviour checks fixed beforehand: routine 36 of 36 checks, demanding 35 of 36 (its one miss was a loose pattern for a nicety, "in-memory"). Both workers also found the one request kind the full-access question hid (`item/tool/requestUserInput`) without being asked. The tasks were too easy to produce a failure at the routine tier, so this is no evidence the routine tier is safe on harder work either.
- **Project routing adds nothing safe.** The frozen keyword rule beat both engines (20 of 22 against 18), and the engines used their own answer in only 11 (Jev) and 16 (Luna) of 32 cases, otherwise falling back to where the thread started. Both engines got the same four wrong: two by falling back to a thread started in the wrong place (`h-subdir-projects`, `h-ys-smith-reconnect`), and two by confidently choosing another project (`h-lead-role` to Agents, `h-usage-harness` to Weave, a request that names Weave) where the thread already sat in the right one, so a router that trusted them would have moved a correct thread.
- **Workflow: a small gain and one dangerous miss.** Jev 24 of 26 and Luna 23 against 19 (current) and 22 (keyword). Luna, the current behaviour and the keyword rule sent all three large settled changes (`h-lead-role`, `h-away`, `h-inspection`) to `solo`; Jev sent two of them there in the final pass and all three in the first. The engines were below their confidence floor and the fallback is `solo`. That is under-processing, the costly direction.
- **Main model: the engines never under-served** (0 cases), and over-served 4 (Luna) and 5 (Jev) against 8 for the current default (always demanding). One of those, `h-explicit-model`, is the user's own "Use Opus", which a constraint applies to every system; it is not a routing error.
- **Hard constraints held.** Both engines disagreed with an explicit user choice once (`h-explicit-model`, main model); the final route kept the user's choice, and no explicit project, workflow or model was ever overridden (0 violations). Constraints are deterministic and applied before and over every classifier and every baseline.
- **Cost of asking:** the 256 held-out calls cost about $0.0031 (Jev) and $0.0045 (Luna) in the service's input-price estimates (mean latency 190 ms and 338 ms), the 64 tuning calls about $0.0008 and $0.0011. These are estimates from the service, not invoices; the decision spend is tiny next to a worker run, whose real cost this pilot did not observe.

Recommendation: **revise.** Keep any future Auto as a shadow recommendation. If the next step is a pilot, take only the subagent tier, recommend routine only above the declared floor, escalate to demanding on every abstention, and record the real outcome and cost of each routed task before any default changes. Project routing needs deterministic rules (a stated project, the repository of the workspace), not a classifier. The workflow fallback must not be `solo` for work that reads as large. Label agreement alone justifies none of this.

## Design

- **Four decisions, asked separately.** One call per case, decision and engine (`rule.ts`): a single `choice` question over the request text only, with the project, workflow or tier definitions (`definitions.ts`) and an explicit `unknown`. The engines never see where the thread started, the baseline, the constraints, the labels or the outcome of the real change.
- **Hard constraints, deterministic** (`constraints.ts`): a stated model ("Use Opus"), a stated project ("In SlipJay, ..."), a stated workflow ("Don't write a Spec", "just talk it through", "Run this as a lead Spec"). Only phrasings of an instruction count, never a mere mention. The classifier cannot override a constraint, and the established route of a thread is kept unless a later message states a change (`settleThreadRoute`, tested). Eligibility is not asked of a model: the only tiers are those of the current managed roles.
- **Abstain and fallback, declared before the held-out run** (`policy.ts`, `POLICY`): an answer is used only when its chosen label has probability 0.6 or more (project, workflow); a tier goes down to routine only at probability 0.75 or more on routine. A failure, refusal, `unknown`, tie or low confidence keeps the current behaviour, which for a tier is demanding. The one tuning change tried (choice floor 0.4) was worse on the tuning set and was reverted: `results/tune-floor-0.4.json`.
- **Baselines, frozen before any held-out call** (`baseline.ts`): `current` (the thread stays where it started, `solo`, always the demanding main model and worker), `keyword` (one frozen keyword and size rule over the text, written by the author with the corpus in view), `routine` (always routine). Every system, `current` included, gets the same explicit constraints applied, since a user who states a choice already gets it today.
- **Cases** (`corpusTune.ts`, `corpusHeldout.ts`): 8 tuning and 32 held-out, with disjoint families. 20 held-out cases are real landed changes in five repositories (15 in this one) restated as a request; 12 are synthetic: chat and no-project questions, explicit constraints, ambiguous requests, and deceptively simple risky changes ("Change the default session timeout...", "Remove the `if (!user) return` guard..."). Where the thread started (`startedIn`) was set by the author, deliberately wrong in six cases.
- **Reference labels** (`results/labels-A.json`, `labels-B.json`): two blind labelers, a different model each (`scout`, deepseek-v4.1-flash low; `implementation-worker` read-only, gpt-6.1-sol medium; an attempt to use sol through `scout` was refused by dispatch and produced nothing), labelled all four decisions of all 40 cases before any engine call, from the text and definitions only, with `unknown` allowed. A label counts only where both agree on a concrete value; a split or any `unknown` is `uncertain` and is reported, not resolved. They agreed on project in 34 of 40 cases, workflow 34, main model 30, subagent tier 32; the scored sets are smaller than 32 because of the uncertain ones (held-out scored: project 22, workflow 26, main model 23, subagent tier 20).
- **Outcome evidence** (`results/outcomes.json`, `buildOutcomes.ts`): for the authentic cases the size and spread of the real landed change. Rework after a change is not measured; later fixes to a busy shared file cannot be attributed to it.
- **Downstream** (`downstream.ts`, `results/downstream.json`): described above. Run against the integration checkout pinned read-only at `bc6277dd25`, not this branch, so the workers could not read the checks.

## Cost, latency and reliability (measured)

Final held-out pass, 128 calls per engine: Jev mean 190 ms, p50 164, max 892, 74,764 input and 8,028 output tokens, about $0.0031; Luna mean 338 ms, p50 313, max 1091, 44,923 input tokens (output not reported), about $0.0045 (the earlier passes cost the same). One Luna call (`h-ys-smith-reconnect`, workflow) returned `refusal`; no call failed, was rate limited or was refused otherwise. Requested and resolved models: `jev-1.14.0` and `gpt-6-luna`, adapter `t3-decisions-v1`.

**Three full held-out passes, and calls whose records are lost.** The T3 server restarted twice during the first pass, which cancelled the shell. The first interrupted run made an unknown number of calls (about a minute's worth, at most a few dozen, well under a cent) and kept no record, because attempts were not yet written as they finished; the harness then began appending each attempt to a log and `--resume` replays it. The second interrupt kept 56 attempts, and the call in flight at the kill is unknown. That first pass finished with 256 attempts (`results/first-run/`). The whole set was then run again, uninterrupted (`results/second-run/`), on source later reformatted and given a lint fix. A review then found that `--resume` could reuse an attempt log under a changed corpus or source, so the log now begins with a run-identity header that a resume must match exactly (`attemptLog.ts`, tested), and a fresh run refuses to append to an existing log. The whole set was run a third time on the final source: `results/heldout.json` is the primary result, its identity matches the code, 256 attempts, no interruption. Across the passes the top-scoring label of the third differed from the first on 3 of 128 Jev calls and 1 of 128 Luna calls, and from the second on 5 and 1; one final route differed from the first pass (a Jev workflow answer, 23/26 against 24/26 in the later two). No call failed in any pass, and Luna returned the same `refusal` for `h-ys-smith-reconnect`'s workflow question each time. The first two passes carry identities that no longer match the files; a test checks only that the primary one does.

## Limitations

- 32 held-out cases (20 to 26 scored per decision), one call per case, decision and engine in each of three passes (almost identical), so repeatability is only shown for the same code, same day; no significance claims, and every interval overlaps.
- The labels come from two models, not people, and they were uncertain or split on 6 to 12 cases per decision; the scored set drops them. The labelers and the engines may share biases. The reference for tier and workflow is a judgement of risk, not an observed outcome.
- The cost ratio and the correction burden are assumptions. No routed worker was run for cost; the downstream check is six easy read-only tasks, one answer per role, and it cannot separate the tiers. The two roles differ in brief and model as well as tier.
- Twenty of 32 cases are restated from real commits after the fact; where a thread started is the author's choice; the keyword baseline was written with the corpus in view, and the engines' abstain floors were set from eight tuning cases.
- Only the request text is used; no conversation history, repository state or attachments. Stable thread intent is enforced by a deterministic rule, not measured over real multi-message threads.
- Provider eligibility and capability are not modelled: the tiers are the two managed roles, and nothing here selects a model.

## Reproducing

From `apps/server`, with the two provider keys already in the environment (`TYPESAFE_API_KEY` for Jev, `OPENAI_API_KEY` for Luna); never pass keys as arguments. Respect the shared 60-per-minute limit (`--gap-ms 2000`).

```sh
node src/decisionEvaluations/autoRouting/run.ts --split heldout --out /tmp/heldout.json --gap-ms 2000
node src/decisionEvaluations/autoRouting/run.ts --split heldout --resume --out /tmp/heldout.json   # after an interruption; refused if the corpus or asking files changed
node src/decisionEvaluations/autoRouting/run.ts --rescore --out src/decisionEvaluations/autoRouting/results/heldout.json   # no provider call
node src/decisionEvaluations/autoRouting/downstream.ts   # scores results/downstream.json
```

Each result records the run identity (checkout `HEAD`, whether the working copy was dirty, the runtime, and the sha256 of every file that decides what is asked or how it is called) and, separately, the scorer files (scoring, labels, policy, baselines, constraints, outcomes). A rescore refuses if any asking file changed. `results/tune.json`, `results/first-run/heldout.json` and `results/second-run/heldout.json` were made on earlier versions of the asking files (before the per-attempt log and `--resume`, formatting and a lint fix), so they no longer rescore; a test checks that their stored summaries still follow from their records. `buildOutcomes.ts` rebuilds `results/outcomes.json` from the five local repositories; `labelPacket.ts` writes the text the labelers read.
