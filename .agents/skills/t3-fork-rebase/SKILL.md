# Bring an upstream nightly into the fork

`t3peach` is the fork: upstream's nightlies merged in, plus the fork's own work. `scripts/fork-nightly.sh` (hourly, launchd) only detects work and dispatches it here, once per attempt: `update` (a new tag to merge, steps 1–9) or `build` (a landed integration to activate: claim, then steps 8–9). This skill is the single path for scheduled, fallback and manual updates, whether the merge is clean or conflicts. Read `fork/README.md` first: its policy decides what to keep. The update lands only through `slipjay land`; never push, force-push or rewrite `t3peach`.

`fork-nightly.sh` below means `~/.t3fork/repo/scripts/fork-nightly.sh`, the installed copy.

1. **Claim.** `fork-nightly.sh attempt <tag> claim <this thread id>`. A refusal names the thread that holds the attempt: stop and report it, unless `t3_thread_read` shows that thread is no longer running, then add `--take-over`. A refusal naming an owner decision, or another attempt that holds every other update back, is never taken over: report it and stop. A refusal saying the tag was superseded names the tag to claim instead. A refusal saying it is already active ends the task. Re-claiming in the same thread resumes the attempt.
2. **Workspace.** Work in this thread's SlipJay workspace; without one, `slipjay start --integration --json "upstream <tag>"` from the integration checkout and do everything there. Record it before anything else: `ws=$PWD; root=$(slipjay status --json | jq -r .integration.root)`; `$root` is the integration checkout, whose git store also holds the workspace's commits.
3. **Merge.** Build the merge in a temporary git clone, based on the workspace's parent (jj commands run in `$ws`, git ones in the clone):
   ```
   base=$(jj log -r @- --no-graph -T commit_id); work=$(mktemp -d)
   origin=$(jj git remote list | awk '$1=="origin"{print $2}'); upstream=$(jj git remote list | awk '$1=="upstream"{print $2}')
   git clone --quiet --filter=blob:none "$origin" "$work/fork" && git -C "$work/fork" remote add upstream "$upstream"
   git -C "$work/fork" fetch --quiet upstream tag <tag> --no-tags && git -C "$work/fork" checkout --quiet --detach "$base"
   git -C "$work/fork" merge --no-edit -m "merge upstream <tag>" <tag>
   ```
   For each conflict, read what upstream changed (`git log -p HEAD...<tag> -- <file>`) and what the fork's side intends (`git log -p <tag>..HEAD -- <file>` and its `fork/differences.md` entry), then write the version the reconciliation in step 4 calls for. For `pnpm-lock.yaml`, take upstream's side, run `vp i` in the clone, and stage the regenerated lockfile. Finish with `git -C "$work/fork" commit --no-edit`. Then bring the merge into the workspace, keeping upstream's ancestry:
   ```
   cd "$ws" && git -C "$work/fork" branch update-merge
   jj git remote add update-merge "$work/fork" && jj git fetch --remote update-merge --branch update-merge
   jj new update-merge@update-merge && jj git remote remove update-merge
   ```
   Every reconciliation edit from here on goes into this one working-copy commit on top of the merge: the gate requires an introduced merge's receipt in the candidate's last commit, so that commit stays last and an answer to a review finding amends it rather than opening another.
4. **Reconcile.** Every update is reconciled, a clean merge included. Start the receipt with `node scripts/fork-upstream-receipt.ts skeleton --repo "$work/fork" --tag <tag> > fork/upstream-receipt.json` (in the workspace), then bound the review to what came in, `git -C "$work/fork" log --stat <baseline>..<tag>`, and the record entries it can affect:
   - Assess the update as a whole before resolving anything, and carry the assessment into the receipt and the report. Sort what came in: additive (`aside`, nothing of ours meets it), colliding with an entry of ours (`overlap`), structural (contracts, migrations, dependencies, a platform service split that reaches force-only code), and entries whose `Retire when` upstream has now satisfied. An `aside` needs only a line; every `overlap` is decided, never left adjacent to ours.
   - Dispose an entry whose exit condition upstream has met rather than keeping it because it still works: `adopt` and retire it, or `adapt` and record what remains with its own removal condition. Two surface implementations of one capability need a recorded reason and an exit condition naming which survives; upstream having built it more carefully is the reason to move, not a reason to keep ours in step.
   - Look for overlap in behaviour, not only in files: upstream adding the same capability under other names, and changes to contracts (`packages/contracts`), dependencies, lifecycles, event ordering, persistence or shared subscriptions that an entry's integration points rely on, even when the fork's files are untouched.
   - Decide each material overlap per `fork/README.md`: `adopt` upstream's implementation when it meets the entry's requirements, `adapt` (upstream's plus the smallest fork extension), `retain`, or `defer` with a `reassessWhen`. Adopting or adapting removes the superseded fork code, triggers, settings and call paths in this change, keeping stored-data, replay and older-client compatibility; a temporary bridge records its removal condition in the entry.
   - Dependencies follow the newer side, never one side wholesale (Decision #6796). In `pnpm-workspace.yaml` and every `package.json`, compare both parents with the merge base per catalog entry, manifest range, override, patch, install permission and release-age exception: keep the fork's where the fork is ahead of upstream, take upstream's where upstream is ahead, and move each with its group in `docs/dependencies.md`. Upstream code written against an older API than the kept version moves to that version's API.
   - Update each affected entry in `fork/differences.md` (decision, evidence, requirements) and the baseline lines; reuse unchanged evidence and #135's measurements rather than rerunning broad benchmarks.
   - Fill the receipt: coverage (upstream commit count, entries considered, areas, exclusions with reasons), dispositions with source/test evidence, unresolved items, the checks you ran and `result: "reconciled"`. Name every entry the record defines in `entriesConsidered`: the gate refuses a receipt that leaves one out, retires one without a disposition, or disposes of an entry the record never defined. A no-overlap result still lists what was covered. Set `reviewer` to this thread and model, `attempt` to the attempt id, and, after your last edit to the record, `record.blob` to `git hash-object fork/differences.md`.
   - An unresolved material loss of functionality, incompatible migration or product choice is Henry's: set `result: "blocked"` with an `owner-decision` item naming the specific trade-off, run `fork-nightly.sh attempt <tag> blocked owner-decision "<trade-off>"`, ask Henry once in this thread and stop. His answer here resumes the same attempt; a later scheduled run never answers it. Missing evidence you cannot obtain is `blocked evidence` the same way.
5. **Check.** `vp i`, the focused tests beside every file you resolved or adapted and those the dispositions name, then `node scripts/test-landing.ts --plan` from the workspace (the gate can list and select tests against the merged config), `jj describe -m "merge upstream <tag>: reconcile"` and `node scripts/fork-upstream-receipt.ts verify --repo "$root" --rev "$(jj log -r @ --no-graph -T commit_id)" --landed "$(jj log -r t3peach@origin --no-graph -T commit_id)"`. Fix a failure the merge caused; one that also fails on the bare tag is recorded in the receipt's checks and left. The full gate runs on the SlipJay runner at landing.
6. **Review the reconciliation, not the merge.** Run `code-review` (scope `change`, as `ticket-reviewer`) over what this update authored: the merge's conflict resolutions, `git -C "$work/fork" show --cc update-merge` — the only hunks where the merge departs from both parents — and the reconciliation commit on top, `jj diff -r @`. The base is the merge, so the reviewed delta is the reconciliation alone. Upstream's own code is out of scope and is never re-reviewed: upstream reviewed it, and reading a nightly's whole diff made this pass cost hundreds of thousands of tokens to re-verify someone else's work. The brief carries the receipt, the record's diff, `git -C "$work/fork" log --stat <baseline>..<tag>` and the resolutions; its Spec axis is `fork/README.md`'s policy, with the record's entries as the checklist. Answer findings as `code-review` says, in the same working-copy commit, and land once they are settled. `scripts/fork-reconcile-fixtures.sh` shows the judgement expected of it.
7. **Land.** `slipjay land` from the workspace. It runs the canonical gate, including the receipt check. If `t3peach` moved meanwhile, the rebased merge has a new fork base and the receipt check refuses it as stale: `jj git fetch`, `jj rebase -s <merge> -d t3peach@origin -d <tag commit>` (a single `-d` replaces both parents and drops upstream's ancestry), reconcile what landed in between (it may touch entries you decided), update the receipt's `fork.base` to the merge's new first parent and anything else that changed, verify, and land again. An interrupted or unknown outcome is followed by running `slipjay land` again, never by a second merge. A failed gate is `fork-nightly.sh attempt <tag> blocked checks "<failure>"`; fix the cause and land again in this thread. Never run `attempt <tag> retry` on your own attempt: it clears `claimedBy` and the scheduler can start a second updater for the tag. `retry` is for another thread or Henry. Once landed, `fork-nightly.sh attempt <tag> landed <operation> <landed commit>`.
8. **Build.** Building installs the runtime on the VPS, which restarts its service. Build unconditionally: an interrupted turn is not a reason to wait, and a landed update that is not built is not delivered. Read the VPS state first only to report what was interrupted, not to decide whether to build — `t3_thread_list` across all environments, and when no VPS environment is linked (this Mac usually has none), `ssh peach-box node - <<'EOF'` running a `node:sqlite` `DatabaseSync` on `/home/ubuntu/.t3/userdata/statev2.sqlite` with `readOnly: true`, selecting `orchestration_v2_projection_runs` rows whose `status` is `preparing`, `queued`, `starting`, `running` or `waiting`; report the count with the build it interrupted. Then `fork-nightly.sh build --attempt <tag>`, which ties the build to your claim so the scheduler can recover it once if it is interrupted; a non-zero exit names why nothing was activated, and `fork-nightly.sh status` shows any partial activation. A refusal naming an earlier build as live or unknown is not yours to pass: report its status line, and use `--take-over` only after confirming that nothing of it still runs. When it names an upstream release or asset that is not published, run `fork-nightly.sh attempt <tag> blocked evidence "<that reason>"` and stop: the scheduler asks again once the release is complete, and the build never takes another version's runtime. Then start the install-on-quit job with `fork-nightly.sh install --on-quit` (never `launchctl submit`, which macOS unloads when the app is force-quit). Never quit the app yourself.
9. **Report** in this thread: the tag and attempt, the conflicts and how they were resolved, the dispositions and any record entries changed, the checks and their results, the landing operation and commit, and `fork-nightly.sh status` (built, staged, installed and active are separate states). Include the update's summary for Henry, written to be read without the diff: what upstream brought, what collided and with which entry, what was adopted or retired and what was kept, what was refused and why, and what is still only ours. Delete `$work`.
