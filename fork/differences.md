# Fork differences

This record lists the material, deliberate differences between the T3peach fork (pechhe/t3code, branch `t3peach`) and upstream (pingdotgg/t3code): capabilities, behaviour changes and temporary workarounds, with the requirements that must survive an upstream update. Every fork change that adds or changes a deliberate difference updates its entry in the same change; upstream reconciliation reads this file to decide retain, adopt, adapt or defer. Entries state requirements and seams, not file catalogues; history lives in git, and tracker items (pechhe/t3code#N) own the work.

### compact-line

- **Kind:** durable extension
- **Why:** A thread's compaction point can differ from its provider's: a long research thread can run further, a noisy one can compact sooner. Compaction itself stays provider-native; T3 sends no context nudges (the earlier context-rollover nudges, holds, `/rollover`, settings and experiment lever were removed in #4361 after a nudge aborted a running compaction).
- **Requirements:** the context bar's auto-compact marker is draggable and sets the thread's compact-at point (`thread.compact-at.set`, null resets to the model's point (the server setting `modelCompactAt`, by model slug and so shared by every Claude instance, set per model in Settings → Providers → Models in thousands of tokens, 67k floor, and written to every environment under the All environments scope), else the provider's "Auto-compact after" setting); double-click or double-tap resets a thread's own point to that default, or opens that provider's settings when the thread already follows it (no "use provider setting" label beside the token count, which would resize the bar as it appeared); the line shows pending until the provider reports the point applied, and with no reported point (Codex on its built-in default) a faded line at the top of the range is still draggable; the point is held to `compactAtBounds` (100k floor for Codex, as its setting has) wherever it is shown or applied. Claude maps the point to `autoCompactWindow` = point + 33k (Claude Code compacts at window − min(maxOutput, 20k) − 13k; window 100k–1M) and Claude Code reads it only at startup (`applyFlagSettings` leaves the live threshold unchanged), so a changed point reopens the session with resume at the next turn, unless background work is running in it; Codex sets `model_auto_compact_token_limit` (scope `total`) at session start or resume, so a live change waits for the next session. Pi compacts natively too, but takes its point only from its own settings file (`compaction.modelOverrides[...].reserveTokens`, default reserve 16k), with no flag, environment variable or RPC command for it, so its line is read-only (`compactAtBounds` returns null); `PiSettings.autoCompactWindow`, or the model's `modelCompactAt`, is written there as `window − point` (never below Pi's 16k reserve) before a Pi session's first turn, turning `compaction.enabled` on with it, and T3 restarts the process it just opened when that write changed anything, so the session runs the point from its first turn; a point changed while a session is already running waits for that session's next start, as Codex's does. The write is taken under a directory lock (the Pi agent dir's `.t3-compaction.lock`, stale after 15s) because Pi's sessions and its own TUI write the same file; T3 records each replaced reserve in `<agent-dir>/.t3-compaction-overrides.json` and puts it back only when the point is cleared. `autoCompactThreshold` reports the point the running process compacts at, not Claude's window, including Claude's default (model window − 33k) and Pi's effective reserve. Stored rollover events, rows, run-setup records and experiment evidence still decode.
- **Integration points:** `compactAt` on the thread contract, the projection and its `compact_at` column; `compactAtBounds` in contracts, shared by server and clients; the Orchestrator's bounds check on `thread.compact-at.set`; `RuntimePolicyV2` resolving the model's point when the thread has none; `modelCompactAt` in `ServerSettings` and its patch (replaced whole), and the server's fold of the briefly shipped per-instance field into it; Claude, Codex and Pi adapters' runtime policy (`modelCompactAt` carries the model's point for providers that cannot take one per thread); `packages/provider-pi/src/server/compaction.ts`; `DeviceContextBar`.

### compact-model

- **Kind:** durable extension
- **Why:** A Claude compaction summarises the whole thread. Once the prompt cache has expired that pass is uncached on whichever model runs it, so a cheaper model saves money; while the cache is warm the conversation's own model is cheaper. The thread must never move to the cheap model, and the summarising model may belong to another account whose subscription or per-token price is cheaper than any Claude model on this one.
- **Requirements:** each Claude instance has `compactModel` (default none), the account it runs on in `compactModelInstanceId` (default this instance) and `compactOnlyWhenCold` (default on); Settings → Providers shows the pair as one picker over every account and model, with accounts that cannot write application text (`isProviderTextGenerationCapable`) disabled. Every `/compact` T3 starts on a Claude thread (compact-on-send, the meter's Compact context, `beforeCacheExpires` idle compaction, a typed `/compact`) is planned at turn start by `ClaudeCompactionPlan` using `chooseCompactionModel` in `packages/shared/src/claudeCompaction.ts`, which the web chip also uses, only to label. Cold means `promptCacheExpiresAt` of the latest usage not marked `compactedWith` has passed; an unknown expiry keeps the conversation's model. The chosen model on this instance travels as the adapter-only `ProviderAdapterV2TurnInput.compaction`, never as the turn's or thread's `modelSelection`, so no `thread.model-selection-updated` is written and the recorded window and threshold stay the conversation's; a chosen model whose window (`ServerProviderModel.contextWindowTokens`) is smaller than the thread's tokens is passed over and the compaction item carries `windowTooSmall`. A session reopened for the compaction keeps the conversation's `autoCompactWindow`. The chosen model on another account (a Sonnet thread whose cache expired compacting on DeepSeek) cannot compact inside this thread's provider session, so `ProviderTurnStartService` writes the summary itself: `renderCompactionTranscript` trims the thread's items to that model's window (first user message and newest items first, `DEFAULT_COMPACTION_WINDOW_TOKENS` when the catalog is silent), the account's `textGeneration.generateCompactionSummary` writes a summary clamped on UTF-8 bytes to `COMPACTION_SUMMARY_MAX_BYTES` (8,000, well inside the 16,000-byte context-handoff cap so any script fits), that summary becomes a `full_thread_summary` handoff with no replayed history (`prepareCompactionSummary`), and the provider thread drops its `nativeThreadRef`, `nativeConversationHeadRef` and `contextUsage` so the next turn opens a fresh session with the summary as its whole conversation. `deliverContextHandoffs` delivers a summary-only handoff whole or fails: it never sends the coverage marker without the summary it stands for, and the marker tells the model the summary replaces all earlier history instead of inviting a read-back. That compaction turn starts no provider turn and settles itself with the completed compaction item (before/after tokens, the model). Dropping the session would strand running work, so it refuses when the thread has background tasks or running subagents, and re-reads the provider thread after the summary call so a session another turn replaced meanwhile is never overwritten with stale state. A summariser failure fails the run and leaves the session in place. The compaction item carries the `model` that summarised; the chip, device flag, send tooltip and the three timeline renderers of that item name it. A failure after a native compaction starts fails on the chosen model.
- **Integration points:** `ClaudeSettings` in contracts (`compactModel`, `compactModelInstanceId`), `resolveClaudeCompactionSetting`, `ProviderTurnStartService` → `RunExecutionService` → `ClaudeAdapterV2` (`contextWindowSelection`, `compactedWith`), `ContextHandoffService.prepareCompactionSummary`, `ProviderTextGeneration.generateCompactionSummary` (every driver through `textGenerationOperations.fromRunner`), `CompactionTranscript`, `ProviderSettingsForm` `model` control with `ProviderSettingsModelPicker`, `contextCompactionLabel` in client-runtime.
- **Proof:** packages/shared/src/claudeCompaction.test.ts, ProviderTurnStartService.test.ts ("Claude compaction model", "Claude compaction on another account": fresh session, failure keeps the session, busy thread refused, warm cache stays native), CompactionTranscript.test.ts, ContextHandoffService.test.ts ("compaction summary"), Adapters/ClaudeAdapterV2.test.ts ("compaction on another model"), ContextWindowMeter.logic.test.ts, ProviderSettingsForm.test.ts, work-log/presentation.test.ts.
- **Upstream:** none; upstream has idle compaction modes (#23037) but no compaction model.
- **Retire when:** upstream lets a compaction pick its own model.
- **Decision:** `retain` (v0.1.3-nightly.20261025.3669, 2026-10-25): the Claude adapter's only change here is upstream's shorter instruction copy (#24850), which carries no upstream `t3_background_wait` block; the summarising model, the cross-account summary path and the compaction item's model are unchanged. ### agent-policy-roles

- **Kind:** durable extension
- **Reviewer role:** `reviewer` judges either `review.scope` (`change` or `spec`). Stored split-role requests, bindings and policy snapshots decode to it without losing scope; version 1 and split version 2 policies remain readable. The Reviewer requires separate `list` (change) and `specList` (Spec) aliases, selected by `review.scope`; split policies retain both exact lists and the change role’s exceptions, while version 1 uses the same list for both scopes. Discovery accepts optional `reviewScope`, defaulting to change, as do role-based schedules without a scope. Settings logic groups both list bindings and preserves them through editing and saving. Both scopes read `roles/reviewer.md`, falling back to the old Spec brief; saving never creates a brief. Forge still requires scope-specific role names: `weaveAgentRole` maps only at that boundary, preserving the reviewer's own identity and run reporting. Contract, policy-service, resolver and Weave recording tests prove these paths. Thread bindings already accepted `reviewer` in the preceding fork; `agent_roles` is MCP-only and does not enter native client RPC payloads. Upstream has no equivalent managed policy in the pinned base; retire this migration when no old stored policies or task records remain.
- **Review council:** the Reviewer's optional `council` flag makes `delegate_task` sit a Spec review as one read-only reviewer per model maker from `specList` (`modelMaker`: slug family, then gateway vendor, then driver), at most five, skipping the author's model; each member's request carries a T3-set `review.councilSeat`, which callers cannot set, is never enrolled in a trial, and its result's `council` lists members, their `taskRef`s and missing makers. Settings → Delegation edits it in the Reviewer row and refuses to save a council of fewer than two makers. An older policy without `council` reads as off. Proof: ManagedDelegation.test.ts (council seating), agentPolicy.test.ts (`modelMaker`, reviewer-only flag), DelegationSettings logic and browser tests. Upstream has no managed policy, so no equivalent.
- **Why:** Delegation uses validated, versioned role/model policy instead of ad-hoc model choice.

### provider-overload-failover

- **Kind:** durable extension
- **Why:** a provider that says it is overloaded can stay that way for hours (Pi's DeepSeek upstream on 5–6 Nov 2026), and the cheap roles that list it first kept starting work on it while the role lists already named fallbacks.
- **Requirements:** a turn item whose failure code says the provider was overloaded (`overloaded` from Pi's upstream `429 … [overloaded]`, Codex's `serverOverloaded`, Claude's `api_error_529`), at a retry's start or on the final failure, marks that run's account and model overloaded for 15 minutes from the latest signal. The record is in memory, so a restart forgets it. ### slipjay-workspace-archive

- **Kind:** durable extension
- **Why:** `git worktree remove` takes a SlipJay workspace with everything a thread wrote outside git — ignored files, a local `.env` — and leaves Jujutsu believing the workspace still exists. Cleanup must retire a checkout SlipJay's way, and a thread that resumes afterwards must get those files back rather than a branch-only checkout that looks complete.
- **Requirements:** a SlipJay workspace is recognised by one rule (a `.slipjay`, `.slipway` or `.pi` home's `workspaces/<name>`, under `HostProcess.HomeDirectory`; a `.jj` marker adds cleanup's reason) that cleanup and turn start both call, and recognising it never pre-empts the gates that keep a running, shared, open-session or unsettled thread's checkout; it is eligible only because its thread was settled or deleted, never for inactivity, while a git worktree keeps its inactivity clock; an eligible one is released by `slipjay retire <path> --operation <id>`, since SlipJay archives the checkout before retiring it, and the operation id derives from the thread, the workspace directory and the settlement (`unsettled` when the thread has none, else its epoch milliseconds), sanitised and capped at 128 characters, so a retry names the same operation and a resumed thread that settles again a new one, which an old attempt can never release; `git clean` is a git-worktree step only, because it would delete the ignored and untracked bytes before SlipJay archives them; whatever SlipJay refuses, cannot confirm, or answers nothing to keeps the checkout and lands in the report with that reason, and a missing or failing `slipjay` is `unavailable`, never permission to fall back to git; a turn whose SlipJay checkout is missing asks `slipjay restore --latest --path <path>` and uses the restored path, and with no archive leaves the path missing so the run fails visibly; before a turn starts on an existing one, `slipjay retire-result --path <path>` fails the run as Release unresolved (`release_unresolved`) when the record says `uncertain` or `retiring`, and lets it start on `retired`, `refused`, no record or no SlipJay at all; every `slipjay` call is bounded at 10 minutes and 4 MB of output.

### landing-test-parallelism

- **Kind:** deliberate behaviour change (test-only; upstreamable)
- **Why:** Landing verification runs test files across eight workers but runs the tests inside one file one after another, so its slowest single files set the floor: Claude's 34 recorded fixture variants plus its extra after-root cases shared one file, OpenCode's 19 and Grok's 16 shared one each, and `migrate-dev-db.test.ts` re-ran the whole migration series for every fixture.

### fork-updater

- **Kind:** durable extension
- **Why:** Upstream nightlies reach the owner's machines unattended, reconciled with the fork's behaviour, without trading away a usable app.
- **Requirements:** every new upstream tag, clean or conflicting, is reconciled against this record and lands only through `slipjay land` with a fresh receipt (no direct push); one attempt per tag is in flight, duplicate deliveries and restarts resume it, a superseded attempt cannot be claimed again, an update supersedes only older tags (a newer tag whose release lost its assets keeps its attempt and is sent again once the release returns), and while an unlanded attempt is claimed and making progress, or waits for an owner decision, no other unlanded tag can be claimed; a claim that goes quiet for a redispatch interval is notified once and no longer holds back a newer published tag, which supersedes it and is sent as the new claim (an owner decision still holds until answered), and a quiet claim on a landed build is only notified, and an update that lands while blocked on publication keeps that block and its `retry` route; an owner decision holds newer tags until answered, and only an attempt still holding its work can record one (a superseded, landed or displaced attempt is refused, so two attempts never hold each other), staying with its holding thread through a late duplicate claim or take-over until Henry answers there or `retry` runs; builds run through the agent, which first checks that no agent turn is running on the VPS; only landed source with a passing receipt check is built and activated, selected by source commit rather than version text; the installed app is replaced only after a complete, signature-verified copy exists, and an interrupted replacement is repaired from the replaced or previous build, with a journal keeping each build's receipt with it; a VPS install that switched the runtime but did not finish, or gave no answer, holds Mac installs until a build confirms the VPS, even when an earlier install of the same version and source had succeeded; an explicit recovery target stays selected until the next build, and source from before receipts is built only as one; failing to keep the replaced app as previous does not undo a finished install, and the next staged build waits until it is kept, so the one-step rollback is always the build immediately before the installed one; a staged build that is no longer the selected target is never installed; a build leads its own process group and records its source, claim, stage and owner identity before work can outlive its launcher, status reads it as live, interrupted or unknown with evidence and a next action and changes nothing, and only an owner and group positively gone, with no remote step left unproved, counts as interrupted; while a build is live or unknown (surviving children, unreadable or reused identity, a PID-only lock from an older script, a VPS step entered with no proved end) the hourly run touches neither the clone nor the claim and a new build is refused unless `--take-over` confirms it stopped; a stopped build with an `--attempt` claim still valid under the attempts lock is recovered through the ordinary build dispatch at most once per landed source and attempt, a repeat is held with its evidence until `attempt <tag> retry` or a new landed source, and an owner decision, recovery target, unassociated build, genuine build failure or a selected build that already satisfies the update is never recovered; the install-on-quit job, started by an agent inside the app, survives the app quitting or being force-quit, detects that quit by pid and start time even when the app reopens between polls, and quits the reopened instance before installing the still-selected staged build and reopening it; ### perf-persistence-writes

- **Kind:** deliberate behaviour change (upstreamable performance fix)
- **Why:** The backend wrote ~200 MB/min into `statev2.sqlite`: every event is its own commit of ~27 WAL pages, and each checkpoint rewrites the pages it touched at random offsets.
- **Requirements:** Claude and Codex persist streamed text, reasoning and plans at most every 400 ms per item (upstream 50 ms for text), under the web reveal's ~0.45 s lag; completion still flushes at once. Allocated event ids end in a time-ordered UUIDv7, so the unique `event_id` index grows at each stream's right edge. The checkpoint worker starts at 4000 WAL frames (upstream 1000); the writer's backstop stays 10 000 frames, but a write is held there only while the checkpoint makes progress: a checkpoint whose end-of-WAL position stands still for 1 s (a reader snapshot pinning the WAL) lets writes through while the worker keeps retrying, and the gate closes again only when the checkpoint passes where it stood at release (or the WAL restarts), so the writes it let through are not mistaken for progress, or at 250 000 frames, so a pin that never lets go cannot fill the disk (upstream holds writes with no bound; a pinned reader held the Mac's writer for 851 s). Each stretch of the gate that held a write is logged once as `sqlite.checkpointGate` (reasons, frames, duration, writes held and released). Projection upserts for turn items, nodes and provider turns write only the columns whose values changed, because SQLite rewrites every index on a SET column even when the value is unchanged; the event log drops the unread `correlation_id` index and keeps `command_id` indexed only where it is set (migration 094).
- **Integration points:** `PROVIDER_TEXT_FLUSH_INTERVAL_MS` in `ProviderTextDeltaCoalescer`; `IdAllocator` event ids (`randomUuidV7`); `CHECKPOINT_FRAMES` and the gate bound (`released`, `armBound`, episode records) in `shared/nodeSqliteClient`'s `startCheckpointWorker`, where upstream's `gated`/`wake`/`runWithAdmission` meet them. `upsertChangedColumns` in `ProjectionStore`; `Migrations/094_EventLogWriteIndexes.ts`.
- **Proof:** packages/provider-core/src/server/IdAllocator.test.ts; packages/shared/src/nodeSqliteClient.test.ts (a pinned reader no longer holds a write, the WAL truncates once it is released, and an episode that held no write is not logged); Claude and Codex adapter streaming tests. Replaying 5,697 real events (11.7 min of live traffic) through `EventSink` on a copy of the 8.3 GB live database: ~1,184 MB written before, ~831 MB after (−30%, runs vary ±5%). Live, the installed app went from ~0.29 to ~0.27 MB written per event. T3-60: replaying 4,000 recorded events (sequence 1245322) through `EventSink` on a copy of an 8.7 GB snapshot, 152.2 → 116.3 KB written per event (1.31x; busy window 166.7 → 122.5 KB), with sidebar, thread-open and full-snapshot reads unchanged within noise.
- **Upstream:** none known; the flush interval, event ids and the bounded gate are upstreamable.
- **Retire when:** upstream persists streaming text less often and stops writing one commit per event, and bounds its checkpoint gate.
- **Constraints:** ACP-based adapters (Antigravity, Grok, ACP registry agents) coalesce streamed text into a snapshot at most every 50 ms (`ACP_TEXT_FLUSH_INTERVAL`, upstream #19626), so they no longer persist one turn-item update per chunk; OpenCode and Cursor were not checked. Each event write costs pages touched, not payload: ~26 pages of 4 KB before T3-60, about half of them the event log's indexes, one leaf each. `idx_orchestration_events_application_sequence` looks unused but the shell's `MAX(sequence)` and the agent catch-up read use it implicitly (dropping it took the shell query from 0.03 ms to 2.8 s). Group commit was measured and rejected (Decision #5594): with durability unchanged it saves under 3%, because live ingestion awaits each write. Smaller pages (1 KB: 2.38x fewer bytes) slow the sidebar and full snapshots by a third or more and were not taken. `orchestration_events` is the live log (rebuild, catch-up, command replay), so streaming events cannot skip it. Shrinking the existing database with a one-off migration is a non-goal: disk has room, and it rewrites live data for no write-rate gain.

### agent-process-ledger

- **Kind:** deliberate behaviour change (upstreamable)
- **Why:** Claude Code runs each command in its own process group and stops them when it gets SIGTERM, but a server that crashes or is killed after the desktop's 5 s quit grace leaves the CLI running, and a CLI killed outright leaves its commands running (builds, `tail -f`, dev servers).
- **Requirements:** OpenCode, detached ACP runtimes (Grok and Antigravity), Pi, Codex app-server sessions and terminal PTY session leaders are recorded under the state directory and forgotten when they exit; at server start, and after the desktop has stopped its servers on quit (waiting up to 3 s for a server it stopped whose stop timed out to exit, and not at all for a live server it did not start), a recorded group whose owning server is gone gets SIGTERM, then SIGKILL after 2 s; a recycled pid (start time, group or command line differ) is never signalled. Codex keeps piped stdio and owns a detached POSIX group through the Effect spawner's POSIX default. Each adopter except OpenCode records its group through `trackUntilExit`, in the background, so spawning never waits on the process-table read; OpenCode keeps upstream's `OpenCodeServerLedger`, which records while the server starts and forgets when its scope closes. Where a runtime also opens a systemd scope, that scope is stopped when the process it launched exits, so a daemon a tool detached with `setsid` stops too, and a runtime that starts again within one session (Pi, for its compaction point) stops the old process's scope and starts the replacement in a fresh one (T3-223).
