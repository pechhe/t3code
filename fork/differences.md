# Fork differences

This record lists the material, deliberate differences between the T3peach fork (pechhe/t3code, branch `t3peach`) and upstream (pingdotgg/t3code): capabilities, behaviour changes and temporary workarounds, with the requirements that must survive an upstream update. Every fork change that adds or changes a deliberate difference updates its entry in the same change; upstream reconciliation reads this file to decide retain, adopt, adapt or defer. Entries state requirements and seams, not file catalogues; history lives in git, and tracker items (pechhe/t3code#N) own the work.

### compact-line

- **Kind:** durable extension
- **Why:** A thread's compaction point can differ from its provider's: a long research thread can run further, a noisy one can compact sooner. Compaction itself stays provider-native; T3 sends no context nudges (the earlier context-rollover nudges, holds, `/rollover`, settings and experiment lever were removed in #4361 after a nudge aborted a running compaction).
- **Requirements:** the context bar's auto-compact marker is draggable and sets the thread's compact-at point (`thread.compact-at.set`, null resets to the model's point (the server setting `modelCompactAt`, by model slug and so shared by every Claude instance, set per model in Settings → Providers → Models in thousands of tokens, 67k floor, and written to every environment under the All environments scope), else the provider's "Auto-compact after" setting); double-click or double-tap opens that provider's settings; the line shows pending until the provider reports the point applied, and with no reported point (Codex on its built-in default) a faded line at the top of the range is still draggable; the point is held to `compactAtBounds` (100k floor for Codex, as its setting has) wherever it is shown or applied. Claude maps the point to `autoCompactWindow` = point + 33k (Claude Code compacts at window − min(maxOutput, 20k) − 13k; window 100k–1M) and Claude Code reads it only at startup (`applyFlagSettings` leaves the live threshold unchanged), so a changed point reopens the session with resume at the next turn, unless background work is running in it; Codex sets `model_auto_compact_token_limit` (scope `total`) at session start or resume, so a live change waits for the next session. Pi compacts natively too, but takes its point only from its own settings file (`compaction.modelOverrides[...].reserveTokens`, default reserve 16k), with no flag, environment variable or RPC command for it, so its line is read-only (`compactAtBounds` returns null); `PiSettings.autoCompactWindow`, or the model's `modelCompactAt`, is written there as `window − point` (never below Pi's 16k reserve) before a Pi session's first turn, turning `compaction.enabled` on with it, and T3 restarts the process it just opened when that write changed anything, so the session runs the point from its first turn; a point changed while a session is already running waits for that session's next start, as Codex's does. The write is taken under a directory lock (the Pi agent dir's `.t3-compaction.lock`, stale after 15s) because Pi's sessions and its own TUI write the same file; T3 records each replaced reserve in `<agent-dir>/.t3-compaction-overrides.json` and puts it back only when the point is cleared. `autoCompactThreshold` reports the point the running process compacts at, not Claude's window, including Claude's default (model window − 33k) and Pi's effective reserve. Stored rollover events, rows, run-setup records and experiment evidence still decode.
- **Integration points:** `compactAt` on the thread contract, the projection and its `compact_at` column; `compactAtBounds` in contracts, shared by server and clients; the Orchestrator's bounds check on `thread.compact-at.set`; `RuntimePolicyV2` resolving the model's point when the thread has none; `modelCompactAt` in `ServerSettings` and its patch (replaced whole), and the server's fold of the briefly shipped per-instance field into it; Claude, Codex and Pi adapters' runtime policy (`modelCompactAt` carries the model's point for providers that cannot take one per thread); `packages/provider-pi/src/server/compaction.ts`; `DeviceContextBar`.

### compact-model

- **Kind:** durable extension
- **Why:** A Claude compaction summarises the whole thread. Once the prompt cache has expired that pass is uncached on whichever model runs it, so a cheaper model saves money; while the cache is warm the conversation's own model is cheaper. The thread must never move to the cheap model, and the summarising model may belong to another account whose subscription or per-token price is cheaper than any Claude model on this one.
- **Requirements:** each Claude instance has `compactModel` (default none), the account it runs on in `compactModelInstanceId` (default this instance) and `compactOnlyWhenCold` (default on); Settings → Providers shows the pair as one picker over every account and model, with accounts that cannot write application text (`isProviderTextGenerationCapable`) disabled. Every `/compact` T3 starts on a Claude thread (compact-on-send, the meter's Compact context, `beforeCacheExpires` idle compaction, a typed `/compact`) is planned at turn start by `ClaudeCompactionPlan` using `chooseCompactionModel` in `packages/shared/src/claudeCompaction.ts`, which the web chip also uses, only to label. Cold means `promptCacheExpiresAt` of the latest usage not marked `compactedWith` has passed; an unknown expiry keeps the conversation's model. The chosen model on this instance travels as the adapter-only `ProviderAdapterV2TurnInput.compaction`, never as the turn's or thread's `modelSelection`, so no `thread.model-selection-updated` is written and the recorded window and threshold stay the conversation's; a chosen model whose window (`ServerProviderModel.contextWindowTokens`) is smaller than the thread's tokens is passed over and the compaction item carries `windowTooSmall`. A session reopened for the compaction keeps the conversation's `autoCompactWindow`. The chosen model on another account (a Sonnet thread whose cache expired compacting on DeepSeek) cannot compact inside this thread's provider session, so `ProviderTurnStartService` writes the summary itself: `renderCompactionTranscript` trims the thread's items to that model's window (first user message and newest items first, `DEFAULT_COMPACTION_WINDOW_TOKENS` when the catalog is silent), the account's `textGeneration.generateCompactionSummary` writes a summary clamped on UTF-8 bytes to `COMPACTION_SUMMARY_MAX_BYTES` (8,000, well inside the 16,000-byte context-handoff cap so any script fits), that summary becomes a `full_thread_summary` handoff with no replayed history (`prepareCompactionSummary`), and the provider thread drops its `nativeThreadRef`, `nativeConversationHeadRef` and `contextUsage` so the next turn opens a fresh session with the summary as its whole conversation. `deliverContextHandoffs` delivers a summary-only handoff whole or fails: it never sends the coverage marker without the summary it stands for, and the marker tells the model the summary replaces all earlier history instead of inviting a read-back. That compaction turn starts no provider turn and settles itself with the completed compaction item (before/after tokens, the model). Dropping the session would strand running work, so it refuses when the thread has background tasks or running subagents, and re-reads the provider thread after the summary call so a session another turn replaced meanwhile is never overwritten with stale state. A summariser failure fails the run and leaves the session in place. The compaction item carries the `model` that summarised; the chip, device flag, send tooltip and the three timeline renderers of that item name it. A failure after a native compaction starts fails on the chosen model.
- **Integration points:** `ClaudeSettings` in contracts (`compactModel`, `compactModelInstanceId`), `resolveClaudeCompactionSetting`, `ProviderTurnStartService` → `RunExecutionService` → `ClaudeAdapterV2` (`contextWindowSelection`, `compactedWith`), `ContextHandoffService.prepareCompactionSummary`, `ProviderTextGeneration.generateCompactionSummary` (every driver through `textGenerationOperations.fromRunner`), `CompactionTranscript`, `ProviderSettingsForm` `model` control with `ProviderSettingsModelPicker`, `contextCompactionLabel` in client-runtime.
- **Proof:** packages/shared/src/claudeCompaction.test.ts, ProviderTurnStartService.test.ts ("Claude compaction model", "Claude compaction on another account": fresh session, failure keeps the session, busy thread refused, warm cache stays native), CompactionTranscript.test.ts, ContextHandoffService.test.ts ("compaction summary"), Adapters/ClaudeAdapterV2.test.ts ("compaction on another model"), ContextWindowMeter.logic.test.ts, ProviderSettingsForm.test.ts, work-log/presentation.test.ts.
- **Upstream:** none; upstream has idle compaction modes (#23037) but no compaction model.
- **Retire when:** upstream lets a compaction pick its own model.
- **Decision:** `retain` (v0.1.3-nightly.20261025.3669, 2026-10-25): the Claude adapter's only change here is upstream's shorter instruction copy (#24850), which carries no upstream `t3_background_wait` block; the summarising model, the cross-account summary path and the compaction item's model are unchanged. ### managed-delegation

- **Kind:** durable extension
- **Why:** Agents delegate to managed subagents (advisors, readers, isolated writers) with enforced scope, independence and follow-up.
- **Requirements:** A configured role policy requires every new `delegate_task` child to be managed; `offPolicyReason` cannot bypass it. Without a configured policy, raw delegation remains available; accepted requests remain replayable. `delegate_task`/`followup` flows: any managed task can be followed up; advisors are reused and wait for published results; pinned read-only helpers share the lead's workspace but serialize with isolated writers; isolated writers validate their workspace at launch and hand back a revision; delegation to any registered project including No project chats; delegation skips models whose accounts are out of usage; idle advisors close per setting; a managed task's browser tabs close when it ends; agents can read their thread's terminal; default child permission level is a setting; a managed role runs with exactly its resolved options, never the delegating thread's own, and discovery and dispatch agree on them (a refusal names every offending option, review field or changed account; options the caller merely echoes from its own thread for the same account and model, such as `fastMode`, that the role does not set are dropped rather than refused, and the refusal names an account with allowance, not a usage-limited one); pending background work of any kind, including a command left running, holds a thread's completion (it reads Waiting, not Ready) until it ends or is stopped, so a delegated result is not reported early; a Stop writes an event only when it changes something, so a repeated Stop on a settled thread writes none.
- **Integration points:** `OrchestratorMcpService` and `orchestrator` toolkit; `ManagedAgentService`, `followup`, `writerWorkspacePreflight`, `workspaceIdentity`; `AdvisorIdleCloseReactor`; provider MCP session wiring (`provider-core`); docs/operations/agent-delegation.md.

- **Kind:** deliberate behaviour change (test-only; upstreamable)
- **Why:** Landing verification runs test files across eight workers but runs the tests inside one file one after another, so its slowest single files set the floor: Claude's 34 recorded fixture variants plus its extra after-root cases shared one file, OpenCode's 19 and Grok's 16 shared one each, and `migrate-dev-db.test.ts` re-ran the whole migration series for every fixture.

OpenCode's v1/v2 protocol choice lives in `OpenCodeReplayRuns.ts`, shared by both of its files. `migrate-dev-db.test.ts` runs the migration series once per file into a template database and copies it per fixture with `VACUUM INTO` before writing only that fixture's rows, so the dev-database behaviour each test asserts is unchanged. ### perf-persistence-writes

- **Kind:** deliberate behaviour change (upstreamable performance fix)
- **Why:** The backend wrote ~200 MB/min into `statev2.sqlite`: every event is its own commit of ~27 WAL pages, and each checkpoint rewrites the pages it touched at random offsets.
- **Requirements:** Claude and Codex persist streamed text, reasoning and plans at most every 400 ms per item (upstream 50 ms for text), under the web reveal's ~0.45 s lag; completion still flushes at once. Allocated event ids end in a time-ordered UUIDv7, so the unique `event_id` index grows at each stream's right edge. The checkpoint worker starts at 4000 WAL frames (upstream 1000); the writer's backstop stays 10 000 frames, but a write is held there only while the checkpoint makes progress: a checkpoint whose end-of-WAL position stands still for 1 s (a reader snapshot pinning the WAL) lets writes through while the worker keeps retrying, and the gate closes again only when the checkpoint passes where it stood at release (or the WAL restarts), so the writes it let through are not mistaken for progress, or at 250 000 frames, so a pin that never lets go cannot fill the disk (upstream holds writes with no bound; a pinned reader held the Mac's writer for 851 s). Each stretch of the gate that held a write is logged once as `sqlite.checkpointGate` (reasons, frames, duration, writes held and released).
- **Integration points:** `PROVIDER_TEXT_FLUSH_INTERVAL_MS` in `ProviderTextDeltaCoalescer`; `IdAllocator` event ids (`randomUuidV7`); `CHECKPOINT_FRAMES` and the gate bound (`released`, `armBound`, episode records) in `shared/nodeSqliteClient`'s `startCheckpointWorker`, where upstream's `gated`/`wake`/`runWithAdmission` meet them.
- **Proof:** packages/provider-core/src/server/IdAllocator.test.ts; packages/shared/src/nodeSqliteClient.test.ts (a pinned reader no longer holds a write, the WAL truncates once it is released, and an episode that held no write is not logged); Claude and Codex adapter streaming tests. ### agent-process-ledger

- **Kind:** deliberate behaviour change (upstreamable)
- **Why:** Claude Code runs each command in its own process group and stops them when it gets SIGTERM, but a server that crashes or is killed after the desktop's 5 s quit grace leaves the CLI running, and a CLI killed outright leaves its commands running (builds, `tail -f`, dev servers).

### run-interrupt-cause

- **Kind:** deliberate behaviour change
- **Why:** Every run that ended `interrupted` was recorded as "Run interrupted by user" and could read "You stopped", including provider aborts and closed queries the user never asked for.
- **Requirements:** the run's `run_interrupt_result` item carries the reason the Stop recorded when one did (a client's reads "Stopped by user", an agent's names the agent and its reason) and otherwise says what actually happened; it also carries `cause`: `user` only when the run has an unpaired interrupt request (a Stop), `move` when the thread moved, else `server-close` when the adapter reports T3 closed the query (`interruptCause` on `turn.terminal`), else `provider-abort`; the message says what happened and never blames the user for the last two; the web timeline never labels a run "You stopped" (a stopped run always carries its interrupt items and is shown as those). A steer supersedes the attempt and writes no interrupt item. Items written before causes decode without one.

### ws-rpc-group-split

- **Kind:** durable extension (a type-system constraint, not a product behaviour)
- **Why:** `RpcGroup.toLayer` types each handler's requirements by scanning every RPC in the group, so its cost grows with handlers × RPCs; near 200 WebSocket methods it crossed TypeScript's instantiation limit and the layer's requirements degraded to `any`. The fork reaches that size before upstream because of its own peers and hq RPC groups.
- **Requirements:** every WebSocket RPC is served through the feature group that owns it (`WsCoreRpcGroup`, `WsPullRequestRpcGroup`, `WsPeersRpcGroup`, `WsHqRpcGroup`), each registering its own handler layer; `WsRpcGroup` is their merge, so `RpcServer.make(ServerWsRpcGroup, …)` still serves every method; a new RPC joins a feature group rather than the core group, and the layer's requirement, error and output types stay typed.
- **Integration points:** `packages/contracts/src/rpc.ts` (the four groups and the `WsRpcGroup` merge); `apps/server/src/ws.ts` (`ServerWs*RpcGroup` middleware wrapping, `ServerWsCoreRpcGroup.toLayer`, `layerWsHqRpc`, `layerWsPeersRpc`, `layerWsPullRequestRpc`).

### thread-transcript-export

- **Kind:** durable extension
- **Why:** A thread's whole conversation can leave T3 as one Markdown document, so a reviewer outside T3 — another agent, or a paid chat with the file attached — reads what was asked, what was said and what was done without scrollback. A lead thread can carry its sub-agent threads with it.
